Data model

A post maps to a vault row, a public repository record and a Markdown file. The service stores posts and account links, and nothing else; a vault folder holds blocks, channels, sources and entities, and a cortex keeps its journal.

ohm is in development. These docs cover the implementation and the work still planned. Built does not mean verified on the live service; see Status and limits.

A post in the vault

FieldTypeMeaning
idString, 13 charactersPermanent identifier, generated once by whichever client creates the post
slugStringThe last segment of the post's address. Mutable. Unique within a vault
label, sublabelStringWhere the post is filed, in the author's own words
visibilitypublic, friends or privateWho the post is for. A new post is private
title, subtitleString, optional
dateTimestamp, optionalWhen the post is from. A mirrored post keeps its original date
bodyMarkdownAs the author wrote it
connectList, up to 32Other posts or web pages this post follows from
addressURL, optionalThe post's address on the author's site, when it is not the one its label and slug give
sourceObject, optionalWhere the post first appeared, if elsewhere: platform, address, and the platform's own ID
siteObject, optionalFields of the author's own site, outside the shared schema
propertiesObjectAnything else the author gave it. Stored, and never published

Identifiers and versions

FormPurpose
Post ID13 characters that sort by creation time, in the form the AT Protocol uses for record keysIdentity. Renaming or refiling a post does not change it. It is also the record key when the post is published
Versionv followed by a SHA-256 digest of the post's contentConcurrency control. Every write names the version it replaces. A mismatch is refused with Changed and the current version
SequenceA counter per vault, advanced by every changeIncremental sync. listPosts with since returns only what changed after a cursor, removals included

A removed post keeps its row with no version, so a client that asks what changed is told that it went.

The published record

A public post is one record of type com.ohmmmm.post in the member's repository, stored under the post's ID. The schema is fixed and the same on every site.

FieldTypeMeaning
bodyString, requiredCommonMark with footnotes. media:ID as an image destination places an attachment
publishedAtDatetime, required
canonicalUrlURI, requiredThe post's address on the author's website
title, subtitleString
updatedAtDatetimeWhen the post last changed after it was published
slugStringThe last segment of the address
label, sublabelStringFree-form, as the author named them
formStringThe kind of object, derived from the content: writing, note, image, gallery, video, audio, file, media, link, embed, quote, list, code or other
connectList of URIsAT URIs or web addresses of what the post follows from
linkObjectFor a link or embed: the page as it described itself
sourceObjectWhere the post first appeared, if not on the author's site
mediaListAttachments, each with an ID unique within the post
siteObjectSite-specific data, namespaced by its own $type

visibility and properties are not part of the record. A post that is not public has no record.

Attachments

An entry in media is an image, a video, an audio recording or a file. Each carries a file, which is a blob stored in the member's repository, and may carry sourceUrl, the address the original came from.

KindAcceptsAdditional fields
imageimage/*alt, caption, width, height
videovideo/*poster, caption, durationMs
audioaudio/*caption, durationMs
fileapplication/*, text/*caption

In the vault, a post references its attachments by address. The copy in the repository is made when the post is published. Mirror and publish

Storage

The service stores posts and account links in two tables.

TableKeyHolds
postsAccount DID and post IDThe post as JSON, its version and sequence, and indexed copies of the fields the repository tree is drawn from
linksohm user ID, with the DID uniqueWhich AT Protocol account an ohm account works in, and when its published posts were first mirrored

The database enforces unique keys and conditional updates.

Vault folder nodes

A vault folder is read as four kinds of node by vault/node.mjs, which is pure: callers pass { path, text } and write what they get back. The lexicons in lexicons/com/ohmmmm/vault/ (block, channel, entity, source, all keyed by TID) describe file contents; none is written to a PDS.

NodePathFields
Block<folders>/<name>.mdkind, title, slug, channels, origin, from, excerpt, tags, by, status, intent, created, updated; the body
Channel<folders>/_channel.md, or any folder holding a blocktitle, kind, order, site; the body is the description
Entity_entities/<kind>/<name>.mdname, aliases, uri; kind from the folder
Source_sources/<id>/source.jsonkind, uri, platform, platformId, title, author, publishedAt, capturedAt, retain, meta

The values each kind of field allows:

ValuesAllowed
Block kindtext, excerpt, link, media, file, code, post
Channel kindcollection, concept, inbox, import
Entity kindperson, work, place, org
Source kindpage, post, file, image, video, audio, thread, book, other
retainreference, text, full
statusproposed, kept, archived
intentprivate, friends, public

A block's folder is its home channel. A file with kind: post, or with no kind and a visibility, is read and written by the unchanged post code, so it keeps its version and syncs as before; channels is stored as an ordinary post property. Unknown properties are kept. IDs are 13-character TIDs, given once; a node without one is keyed by its path until it has one. readNode(nodeFile(n)) gives back n for any node that was read, and problems come back as sentences rather than errors.

Evidence edges

evidence(vault) returns { kind, from, to, at } for each edge, from content alone.

KindFrom
containsA block's folder or channels list; a folder inside a folder
linksA double-bracket link, a web or at:// link, a post's connect
embeds![[file]] or ![[block]]
mentions@handle, matched to an entity's slug, name or aliases
from, quotesA block's from and excerpt

at is a body line number, or the property the edge came from. A target is a node key, url:, at:, file:<name>, or missing:<as written>. Fenced code, inline code and e-mail addresses are skipped. Inference has no edge kind here: it is a cortex node that cites a block as {node, version}.

The index

.vault/index.sqlite, written only by scan in vault/indexer.mjs, holds the tables meta, files, nodes, edges, terms and problems. It is derived data: a different index version drops and recreates it, a damaged file is set aside and recreated, and nothing in it is the only copy of anything. A file is reread only when its inode, size, modified time or changed time moves, and addressed by a CIDv1 of its bytes; a reference root is never opened and has no address. Search uses its own word table with character bigrams for Korean, Japanese and Chinese. The agent reference has the full contract.

The cortex journal

ohm-cortex keeps one append-only file, .cortex/journal.jsonl. Every line has seq, a unique id, at, actor ({kind: "human" or "agent", name}), sometimes session, and a type.

typeHolds
changenode, op (create, update, remove, restore), before and after versions, reason, evidence; proposedBy for a confirmed identity fact or an approved skill
noteOne observation, with evidence. Changes no file
settledWhat became of a note
sessionsummary, outcome, made (change IDs), project, deadEnds (tried, why, check), resolved
saveA name and a note. Changes nothing

Nodes are named identity, playbook, memory/<name>, working/<agent>, skill/<name>, tool/<name> and channel/<path>. Earlier versions are kept in .cortex/history/ by version hash. Evidence pointers are {node, version} or {session}. Lines are ordered by time, then ID, so two machines' journals join by union. Older proposal and decision lines are read and change nothing. No line records what an agent read.
